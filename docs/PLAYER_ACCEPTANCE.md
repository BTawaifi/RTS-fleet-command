# Player acceptance and definition of done

**13 October 2026 · RTS Fleet Command 1.4.5**

Scope: the eight gameplay requests, subsequent missile/weapon/camera regressions, station tooltip and insignia issues, RTS-menu level restart, and the [philosophy divergences](PHILOSOPHY_AND_GAMEPLAY_RECOMMENDATIONS.md#divergences-from-the-philosophy--13-october-source-audit). Recovery means station service; withdrawal protection means covering a departing ship. There is no escape-pod collection, crew-transfer or rescue-ship requirement.

This contract supplements [AI acceptance and invariants](AI_ACCEPTANCE_AND_INVARIANTS.md). It defines future acceptance; it does not certify that the matrix below has been executed.

## What done means

A criterion is **DONE** only when its scenario and legitimate control pass on the retained code, its required evidence is recorded, and its shared-path regression checks pass. The original defect must be reproduced or the covering regression must demonstrably fail with the responsible fix removed. For an unreproduced reported crash, successful alternative scenarios establish limited coverage, not resolution of that incident.

Use **PENDING** for unfinished implementation/testing, **BLOCKED** for a named missing observation or engine capability, **FAILED** for an executed failure, and **DONE** for completed evidence. Keep implementation status separate from acceptance status. Do not replace an unknown with a pass, treat an observation cap as a draw, or count a skipped/missing test as exercised coverage.

The complete request is DONE when G01–G11 and P01–P08 pass, the final diff is reviewed, the automated gates below finish successfully, and the player-facing checks receive an explicit reviewer verdict. A limitation may close a criterion only after the user explicitly accepts that limitation; retain its evidence and scope. Committing code is a checkpoint, not gameplay acceptance or publication.

## Evidence and coverage

For every execution, record criterion ID, Git commit plus any uncommitted diff fingerprint, engine version/hash, asset packages, resolution, faction/profile/class/loadout, setup, seed, initial conditions, actions, elapsed mission time, expected/actual result, verdict and artifact paths. Retain failed attempts alongside successful ones. Test instrumentation, simulated input and invulnerable fixtures must be disclosed.

- Native correctness: installed stock FSO 26.0.1 and the clean upstream review build. Record their actual identities; neither may depend on the modified experiment engine.
- Assets: retail-only and installed optional MediaVPs with the mod's matching patches. Unsupported asset combinations are explicitly outside the result.
- UI: 1280×720, 1920×1080 and 2560×1440, or a supported equivalent when the available display cannot render that size. An unrendered size remains pending; geometry doubles do not substitute for its pixels.
- Profiles: inspect all nine political profiles, including mirrored opponents and changed team colors. Exercise every available station track, sentry option and ability description. Enumerate these from config rather than assuming a fixed count.
- Weapons: enumerate each roster class with native primary/secondary banks; classify coverage by ordinary homing, aspect-lock, swarm, nonhoming, bankless and turret-equipped behavior. Include a positive control for each available family. A representative class does not certify the remaining loadouts.
- Shared lifecycle: manual control and Auto Mode; command, pilot, pause, service, withdrawal, station loss, aftermath and restart. Each relevant transition must preserve ownership, ammunition, histories and resource accounting.

## Philosophy criteria

| ID | Scenario and control | Pass condition and required evidence |
| --- | --- | --- |
| P01 Identity and attachment | Commission a named wing; damage, service and pilot a member; lose/withdraw members; recycle a native signature and restart. Control: undamaged rearm and replacement ship. | Original lifetimes/membership and factual events reconcile with real hulls; replacement receives a new identity; undamaged rearm is not a damaged recovery; intro/setup actors are absent from real history. A viewer can identify a returning ship and its original wing using the existing UI. Record histories/report plus reviewer observations. Emotional attachment is player feedback, not a numerical invariant. |
| P02 Crew-aware recovery priorities | Equally injured capital vs fighter; moderately injured capital vs two critically injured fighters; older fighter admission vs later capital, using the frozen two-slot fixture. Repeat with four configured slots and reserved injury/timing variants. | Labeled exposure bands, missing hull and occupied slots produce the declared admission/work order, while FIFO and explicit commands remain intact. Healthy large ships gain no injury priority. Smaller crews can outrank a larger hull under the declared control. Actual paid repair and useful rejoin occur; no free resets or indefinite starvation. These results certify bounded service priority, not a maximized lives-saved count. |
| P03 Preservation versus necessary risk | Freeze (a) an endangered ship with a feasible service/withdrawal route and no useful continuing attack, (b) a threatened ship holding an essential objective/cover task, (c) competing protection choices involving one large and several small crews. Pair each with a near-identical control changing objective necessity, route feasibility or risk to covering ships. | Before implementation/testing, state the expected choice and rationale from crew exposure, route feasibility, threat and objective. The commander makes the declared choices and produces recorded physical/objective outcomes; no unconditional size-first retreat or healthy-capital hiding. Explicit player attack/hold/pilot orders remain authoritative. Current broader crew-aware escort/rearguard decisions are PENDING, not implied by P02. |
| P04 Useful recovery and protection | Repeat at least three real hostile-injury → paid service → rejoin cycles on one lifetime; cover a departing ship with and without an actual pursuing threat. | Histories, costs, slots, losses and useful combat participation reconcile across cycles. Protection is demonstrated by observed threat interaction and beneficiary outcome, not proximity or an assigned cover label alone. There is no new rescue/pod/crew-transfer mechanic. |
| P05 Courage and factual commendations | Positive/negative cases for recovery/rejoin and withdrawal cover; friendly injury, beam contact without measured hull loss, repair alone, station kill, repeated callbacks, signature reuse, recipient loss and restart. | Both implemented citations require their frozen factual evidence, appear once per lifetime with a readable reason, survive observed loss/escape within the match, reset on restart and grant no economic/stat bonus. Reviewer can explain why the award was earned. Broader gallantry, distinguished-service, justified-sacrifice categories and wing awards remain PENDING: each needs an agreed observable contribution, attribution rule and near-identical nonqualifying control before it can be DONE. Death alone never qualifies. |
| P06 Survivor agency and restraint | Destroy one station while rivals survive; observe defeated AI cover/extraction; manually withdraw Blue; honor then deny passage; explicitly intercept; destroy the final station and continue survivor combat. Include a stranded hull. | Loss of command never silently deletes living fleets. Other surviving commands retain their legitimate economy until global aftermath. Original strategic result stays immutable while mobile fates and later losses update. Autonomous passage is obeyed, explicit interception/in-flight damage remains possible, and only confirmed native departure records escape. Physically feasible survivors finish their fates; stranded cases are reported. Record original/current reports, orders, production and departure events. |
| P07 Intro and readability | Watch normal intro, skip each shot, restart level, enter setup and START; repeat with mirrored factions and optional assets. Ask a viewer to explain the sequence without coaching. | Viewer identifies rival commands, escalation, command responsibility and crew stakes. Captions are legible; transitions/frame composition are acceptable; wording does not impose a fixed three-faction canonical war. Temporary actors alter no real CP, fleet ownership, histories or losses. Native life-cycle checks and final pixel review both pass. |
| P08 Honest reporting and long-match acceptance | Reconcile reports against event/history data after service, withdrawal, station loss and aftermath. Execute the predeclared balance/control/reserved-seed plan in AI_ACCEPTANCE_AND_INVARIANTS.md on the retained candidate, preserving unresolved caps and failures. | Reports distinguish station result, mobile losses/escapes/presence, stranded ships and after-result losses; no invented crew-death/head-count, moral grade or hidden enemy-order disclosure. Selected evidence supports the declared balance/participation guardrails. Reviewer can understand recovery/withdrawal and the distinction between victory and survival. Missing categories/coverage are named; old cohorts do not validate later code. |

## How to execute the checks

From the repository root, after gameplay code changes:

```powershell
python -m pytest core/tools -q --tb=short
git -c core.safecrlf=false diff --check
```

Use owning suites while iterating: `test_pilot_fire.py`, `test_pilot_capital.py`, `test_player_feedback.py`, `test_camera_director.py`, `test_environment.py`, `test_station.py`, `test_service.py`, `test_fleet_life.py`, `test_feature_request.py`, `test_hud_layout.py` and `test_review_regressions.py`. Existing parser/global/scope tests are part of the full suite. Do not run a name filter and describe it as shared-path coverage. Kill the relevant covering assertion against the original mechanism; retain red/green evidence.

The sibling `RTS-fleet-command-artifacts/headless/headless.py` launches frozen native fixtures. First inspect `probe --help`; use fresh tags and distinct ports. For example:

```powershell
python '../RTS-fleet-command-artifacts/headless/headless.py' probe '<fresh-tag>' --kind lifecycle --rendered --port 49201
python '../RTS-fleet-command-artifacts/headless/headless.py' probe '<fresh-tag>' --kind feedback --rendered --port 49202 --ui-seconds 3
python '../RTS-fleet-command-artifacts/headless/headless.py' probe '<fresh-tag>' --kind commands --rendered --port 49203
python '../RTS-fleet-command-artifacts/headless/headless.py' probe '<fresh-tag>' --kind crew --rendered --port 49204
python '../RTS-fleet-command-artifacts/headless/headless.py' probe '<fresh-tag>' --kind extraction --rendered --port 49205
```

Those examples select the runner's configured clean upstream build. To claim installed-26.0.1 coverage, launch that executable against the same isolated fixture and record its exact command/hash, campaign and graphics flags; do not relabel a 26.1.0 run as 26.0.1. Optional MediaVP verification uses the runner's documented `--mediavps` option and records the actual package versions. These fixtures cover selected scenarios, not the complete matrix or real user-input/pixel checks.
